Hier is je **final-mile Replit script**:

```text
Act like a senior TypeScript full-stack engineer working in an existing Vite + React + Express + Drizzle/Postgres codebase.

Your task is to finish the final-mile validation and hardening of the current OpenRegio app so we can determine whether it is truly ready for staging/live use.

Context:
The codebase already passes:
- `npm run check`
- `npm run build`

Startup robustness has been improved:
- missing required env vars fail clearly
- optional integration keys no longer break boot
- seed/bootstrap failures are more controlled

Now the remaining goal is to verify and tighten the runtime/integration layer.

Goal:
Take the app from “mostly green” to “as close to fully green as possible” by validating the live/runtime path and hardening the remaining integration and database behavior with minimal changes.

Important:
- Do not add new product features
- Do not redesign the UI
- Do not broadly refactor unrelated code
- Keep changes minimal, targeted, and readable
- Preserve existing routes, business logic, auth, and data flows
- Everything must remain type-safe and buildable

Main objectives
================================================================

1. Validate real startup path with database
Using the current project setup, verify the app starts correctly with:
- a valid `DATABASE_URL`
- a valid `SESSION_SECRET`

Requirements:
- confirm the app boots cleanly with a reachable Postgres database
- confirm migrations/schema setup is not silently broken
- confirm startup logs are clean and understandable
- if migrations or DB init still fail in a recoverable but messy way, tighten that behavior

If the project uses Drizzle push/migrate patterns, verify the intended startup path is correct and document it clearly.

2. Verify login/auth flow end-to-end
Test the real login/session flow in the existing app structure.

Requirements:
- verify login works
- verify protected dashboard access works
- verify session persistence works after refresh
- verify logout works if implemented
- verify unauthorized users are correctly redirected or blocked from protected routes

If auth behavior is broken or ambiguous, fix only the minimal code required.

3. Verify dashboard access after login
Since the dashboard is central to the product, verify:
- authenticated user can reach the real logged-in dashboard
- dashboard loads without crashing
- any key queries or user-dependent UI render safely
- if some dashboard data is missing, the page still renders cleanly

If there are runtime dashboard crashes, fix them minimally.

4. Verify Intel Dashboard route
Check whether `/intel` now exists in the app.
If it exists:
- verify it is protected behind login
- verify it renders cleanly
- verify its API/data path does not crash
If it does not exist yet:
- do not invent it in this task unless it is already partially wired
- simply document that it is not yet part of the validated runtime scope

5. Verify database-dependent behavior
Inspect and validate the critical DB-dependent flows already present.

Examples:
- user/profile lookup
- any seed/bootstrap account logic
- any dashboard or user queries
- subscriptions/payment status if already wired

Requirements:
- DB errors should fail clearly
- no obvious unhandled query crash on normal login/dashboard flow
- startup should not repeatedly create chaotic side effects

6. Verify Mollie integration path
Do not redesign it. Validate it.

Requirements:
- inspect whether checkout route/path is wired correctly
- inspect whether callback/return handling is wired correctly
- inspect whether webhook route exists and is safe
- verify missing `MOLLIE_API_KEY` fails gracefully
- if possible, test with safe placeholders or test mode assumptions without breaking code
- if a minimal issue blocks production usage, fix it

Important:
- only make minimal changes
- focus on reliability and clarity of failure modes
- do not build a new payment system

7. Verify Postmark/email path
Requirements:
- inspect onboarding/email sending logic
- verify missing `POSTMARK_API_KEY` fails gracefully
- ensure routes/pages do not falsely claim email was sent when it definitely was not, if that is currently happening
- if needed, improve messaging or backend result handling minimally and safely

8. Verify live/staging environment requirements
Create or update a clear minimal environment contract for staging/live.

Separate:
- required to boot
- required for auth
- required for payments
- required for email
- optional AI/integration keys

If an `.env.example` already exists, update it only if needed.

9. Keep the project green
After all work:
- `npm run check` must pass
- `npm run build` must pass

10. Provide go/no-go output
At the end, provide an honest status:
- what is fully green
- what is still orange
- what is still red if anything remains
- whether the app is ready for:
  - local dev
  - staging
  - real production use

Constraints
================================================================

- No broad refactor
- No new features
- No UI redesign
- No replacing auth/payment/email systems
- No new architecture
- Keep changes minimal and operationally meaningful
- Preserve current business logic and routes as much as possible

Suggested work order
================================================================

1. Inspect startup path and DB init path
2. Boot app with real/working DB assumptions
3. Validate auth/login/dashboard flow
4. Validate `/intel` only if already present
5. Validate payment and mail integration paths for graceful behavior
6. Tighten any final runtime issues
7. Re-run:
   - `npm run check`
   - `npm run build`

Expected deliverables
================================================================

When done, provide:
1. Files changed
2. What runtime issues were fixed
3. Auth/login/dashboard validation results
4. Intel route validation result
5. Mollie validation result
6. Postmark/email validation result
7. Minimal required env vars for:
   - boot
   - payments
   - email
8. Results of:
   - `npm run check`
   - `npm run build`
9. Final status as:
   - green
   - orange
   - red
10. Final recommendation:
   - ready for local use
   - ready for staging
   - ready for production
   - or not yet

Definition of done
================================================================

This task is only done when:
- the real runtime path has been validated as far as possible
- key auth/dashboard behavior has been checked
- payment/email failure modes are clearer and safer
- environment requirements are clearly documented
- `npm run check` passes
- `npm run build` passes
- the final output gives a real go/no-go assessment
```
